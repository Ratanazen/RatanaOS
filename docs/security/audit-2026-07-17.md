# RatanaOS security audit — 2026-07-17

## 1. Security summary

RatanaOS Phase 1 is a small Debian `live-build` image factory. The reviewed tree
does not yet contain a custom kernel, drivers, system calls, privileged desktop
applications, package sources, or an installer implementation. No hardcoded
credentials, private keys, world-writable repository files, or obvious shell
injection paths were found. The existing static test suite passes.

The largest current risk is the release supply chain: builds run in a privileged
container using moving base/package inputs and tag-based GitHub Actions, while
published images have checksums but no authenticated signatures or provenance.
These limitations are already partly acknowledged in the architecture and Phase
1 documentation, but they must be resolved before distributing a production
release.

Scope reviewed: tracked source and shell scripts, live-build configuration,
package list, branding overlays, GitHub Actions, repository permissions, and
project documentation at commit `a6e1b80`. Locally untracked files were not
treated as approved release inputs.

## 2. Critical issues

None identified in the current Phase 1 source tree. This is not a production
security approval: Secure Boot, signed artifacts, reproducibility, installed
system policy, and runtime testing are incomplete.

## 3. Medium issues

### M1 — Privileged, mutable CI supply chain

Both workflows run `debian:stable` with `--privileged`, install unpinned packages
from the current mirror, and reference actions by mutable major-version tags.
The release workflow additionally grants `contents: write`. A compromised or
unexpected upstream input therefore executes with broad build-runner capability
and may affect release artifacts. The moving inputs also prevent reliable
reproduction of a reviewed image.

Recommended action: pin the container by digest, pin Debian to a codename and
snapshot for releases, record the complete package manifest, pin every action to
a full commit SHA, and isolate the privileged image-build job from the minimal
release-upload job. Use protected environments/tags and require approval for the
release job.

### M2 — Release artifacts are not authenticated

The pipeline publishes an ISO and SHA-256 file, but both originate in the same
workflow and are uploaded without a detached signature, key policy, SBOM, or
build provenance. A checksum detects accidental corruption but does not
authenticate the publisher.

Recommended action: sign the checksum/ISO with an offline-controlled release
key or a reviewed keyless signing workflow; publish verification instructions,
an SBOM, package manifest, source revision, build-input metadata, and SLSA-style
provenance.

### M3 — Boot and installed-system hardening is not defined or tested

Secure Boot is deferred, and the repository contains no explicit firewall,
AppArmor, kernel sysctl, GRUB password/edit policy, disk-encryption default,
login policy, or live-user sudo policy. Debian defaults may be reasonable, but
they are not a RatanaOS security specification and can change with moving
packages. The boot test is interactive and does not verify these controls.

Recommended action: define a versioned hardening baseline, explicitly inspect
the generated live user and sudoers policy, enable/test AppArmor and nftables,
document inbound-service defaults, test encrypted installation and recovery,
and add BIOS/UEFI/Secure Boot checks before a production release.

### M4 — Dependency vulnerability state is neither pinned nor scanned

The package list names packages without versions, `stable` moves over time, and
CI performs no vulnerability, license, or SBOM scan. Consequently the exact
dependency set cannot be reviewed from this repository and a later build can
differ materially from the audited one.

Recommended action: generate and retain package/version/source manifests for
each build, scan the resulting filesystem and SBOM, define severity exceptions
with expiry dates, and fail releases on unresolved critical vulnerabilities.

### M5 — Predictable privileged temporary file

`tests/smoke-iso.sh` redirects `xorriso` output to the fixed path
`/tmp/ratanaos-el-torito.txt`. When the test runs as root on a shared host, a
local attacker could pre-create a symlink and cause truncation of another file.

Recommended action: use `mktemp`, install a trap that removes the file, quote
the resulting path, and avoid running the smoke test as root when it is not
required.

## 4. Low issues

### L1 — ISO smoke validation is too shallow

The test accepts the presence of an El Torito option and prints a checksum, but
does not independently verify BIOS and UEFI boot, SquashFS integrity, expected
files, package manifest, image permissions, or installed-system behavior. QEMU
testing is manual and always requests KVM.

### L2 — Static analysis coverage is minimal

The test suite checks syntax and a few metadata strings. It does not run
ShellCheck, actionlint, YAML validation, secret scanning, permission-policy
tests, or destructive-path tests. The template renderer also substitutes values
directly into `sed`; current validation makes `VERSION` safe, but future template
variables should receive equivalent validation.

### L3 — Generated configuration is replaced wholesale

`configure-build.sh` recursively removes three generated configuration
directories before recreating them. The paths are currently fixed beneath the
repository, but this design can silently discard newly added generated inputs
unless every source is wired into the script and tests.

### L4 — Placeholder identity URLs ship in branding

`os-release` contains `ratanaos.example` support and issue URLs. This is not a
direct vulnerability, but production users would lack a trusted reporting and
security-advisory channel.

## 5. Recommended fixes

Prioritized remediation order:

1. Replace the fixed `/tmp` path and add ShellCheck/actionlint to CI.
2. Pin GitHub Actions, the Debian container, suite, mirror snapshot, and package
   inputs; emit a package manifest and SBOM.
3. Split build and publication privileges, protect release tags/environments,
   and authenticate artifacts with signatures and provenance.
4. Define and test the live/installed security baseline: sudo, firewall,
   AppArmor, enabled services, sysctls, bootloader, encryption, updates, and
   recovery.
5. Add automated QEMU BIOS and UEFI tests, followed by Secure Boot positive and
   negative tests when signing is implemented.
6. Add continuous vulnerability scanning of both build dependencies and the
   finished image, with a documented triage and exception policy.

## 6. Code quality score

**7/10 for Phase 1 build code; not production-ready.**

Strengths include strict Bash modes, consistent quoting, small scripts,
centralized build variables, HTTPS mirrors, least-privilege read permissions in
the normal build workflow, clear architecture documentation, and a passing
baseline test suite. The score is reduced by mutable dependencies, shallow
automated validation, the fixed temporary path, privileged CI coupling, and the
absence of authenticated release controls.

## 7. Next security tasks

- Review the generated `live-build` tree and final ISO rather than source alone.
- Boot-test BIOS and UEFI and capture automated evidence for enabled services,
  open ports, users/groups, sudoers, file capabilities, SUID/SGID files,
  AppArmor state, sysctls, mount flags, and update configuration.
- Generate an SBOM and scan the image with two complementary vulnerability
  sources; retain results with the artifact.
- Threat-model the installer before custom storage or privilege code lands.
- Establish Secure Boot key ownership, rotation, revocation, and recovery
  procedures before implementation.
- Add kernel-specific review gates if RatanaOS introduces kernel patches,
  out-of-tree modules, drivers, or custom system calls. At present those areas
  are inherited from Debian and were not present for source review.
- Re-audit privileged desktop applications and PolicyKit rules when they are
  introduced.

## Validation evidence and limitations

- `./tests/run.sh`: passed all 15 checks.
- Bash syntax validation: passed for all current scripts and tests.
- Secret-pattern scan: no credentials or private-key markers found.
- Repository mode scan: tracked data files are non-executable; scripts/hooks are
  executable; no world-writable project file was found.
- ShellCheck, actionlint, image build, ISO inspection, QEMU, SBOM, and dependency
  vulnerability scans were not run because their tools/build artifacts are not
  available in this environment.
